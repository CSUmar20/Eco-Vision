# EcoVision

EcoVision is a mobile-first application that identifies a photographed household item and is being built to provide source-backed disposal guidance for the recycling program selected by the user.

The long-term product promise is:

> EcoVision identifies household items and reports whether the user's selected local recycling program accepts them, without tracking the user's precise location.

An item being technically recyclable does not mean every curbside program accepts it. EcoVision should therefore describe an item's status within a named municipality or waste program rather than call it universally recyclable.

## Current MVP

The current vertical slice can:

- Select an image from the device photo library or open the device camera.
- Preview the selected image.
- Upload JPEG, PNG, or WebP images up to 10 MB.
- Classify the image using a configurable Hugging Face zero-shot image model.
- Display the top prediction, confidence, and alternative predictions.
- Save the scan and its predictions in PostgreSQL.
- Let a guest confirm the top prediction or select one of the returned alternatives.
- Preserve the selected image and allow the user to retry after an error.

The MVP does **not** yet determine whether the item is accepted by a local recycling program. API responses explicitly report `local_rules_not_checked` until verified local-rule data is implemented.

## Planned location-aware guidance

EcoVision does not need exact coordinates. A future onboarding or scan flow should ask the user for a general disposal area:

- Country
- ZIP or postal code, or a manually entered city and state/province
- Confirmed municipality or county
- Waste provider when multiple programs serve the same area

The application should store a normalized recycling jurisdiction rather than a precise address or live GPS trail. Local guidance should include its official source, the date it was last verified, and one of these states:

- Accepted curbside
- Not accepted curbside
- Special drop-off required
- Local rule unavailable or unclear

## Architecture

```text
Expo mobile app
    |
    | multipart image upload
    v
FastAPI /classify
    |
    +--> Pillow image validation
    |
    +--> Hugging Face CLIP zero-shot classification
    |
    +--> SQLAlchemy Scan model
              |
              v
         PostgreSQL 18
```

Repository layout:

```text
backend/
  app/                 FastAPI application, database model, and classifier
  migrations/          Alembic database migrations
  tests/               Isolated API and classifier tests
  .env.example         Backend environment template

mobile/
  src/app/             Expo Router screens
  src/api/             Typed backend client
  src/config/          Mobile runtime configuration
  .env.example         Mobile environment template

compose.yaml           Local PostgreSQL service
```

## Prerequisites

- Python 3.12
- Node.js and npm
- Docker Desktop or another Docker-compatible runtime
- Xcode with an iOS Simulator for iOS development

The project currently targets Expo SDK 57. The installed Expo Go version must support the project's SDK. When the App Store version does not match, use an iOS Simulator or an Expo development build instead of downgrading the project.

## Initial setup

Clone the repository, then create the backend environment file:

```bash
cp backend/.env.example backend/.env
```

Replace the example PostgreSQL password in `backend/.env`. Keep this file local; it is ignored by Git.

Create the Python environment and install the locked backend dependencies:

```bash
cd backend
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements-lock.txt
cd ..
```

Install mobile dependencies and create its local environment file:

```bash
cd mobile
npm install
cp .env.example .env.local
cd ..
```

## Start the application

Run each component in a separate terminal.

### 1. PostgreSQL

From the repository root:

```bash
docker compose up -d postgres
docker compose ps
```

The database is exposed only on `127.0.0.1:5432` and stores its data in the `postgres_data` Docker volume.

### 2. Database migrations

From `backend/`, with the virtual environment activated:

```bash
alembic upgrade head
```

Useful migration commands:

```bash
# Show the current revision
alembic current

# Create a migration after changing SQLAlchemy models
alembic revision --autogenerate -m "describe the schema change"

# Revert one migration
alembic downgrade -1
```

Review autogenerated migrations before applying them. Do not edit a migration that has already been applied to a shared environment; create a new migration instead.

### 3. FastAPI

From `backend/`:

```bash
source .venv/bin/activate
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Confirm the service is running:

```bash
curl http://127.0.0.1:8000/health
```

Expected response:

```json
{"status":"ok"}
```

Interactive API documentation is available at `http://127.0.0.1:8000/docs`.

### 4. Expo

From `mobile/`:

```bash
npx expo start --clear
```

Common targets:

```bash
# iOS Simulator
npx expo start --ios

# Android Emulator
npx expo start --android

# Web
npx expo start --web
```

The iOS Simulator has no real camera hardware. Add a JPEG or PNG to the simulated photo library and use **Choose from library** when testing the scan flow.

## Environment variables

### Backend: `backend/.env`

| Variable | Purpose | Example |
| --- | --- | --- |
| `POSTGRES_DB` | Database created by the PostgreSQL container | `ecovision` |
| `POSTGRES_USER` | Local database user | `ecovision_app` |
| `POSTGRES_PASSWORD` | Local database password | Set a private local value |
| `DATABASE_URL` | SQLAlchemy connection URL | `postgresql+psycopg://...@127.0.0.1:5432/ecovision` |
| `HF_MODEL` | Hugging Face model identifier | `openai/clip-vit-base-patch32` |
| `MAX_IMAGE_BYTES` | Maximum accepted upload size | `10000000` |

### Mobile: `mobile/.env.local`

| Environment | `EXPO_PUBLIC_API_URL` |
| --- | --- |
| iOS Simulator | `http://127.0.0.1:8000` |
| Web on the development Mac | `http://127.0.0.1:8000` |
| Android Emulator | `http://10.0.2.2:8000` |
| Physical device | `http://<MAC_LAN_IP>:8000` |

When testing from a physical device, start FastAPI with `--host 0.0.0.0`, keep the device and Mac on the same network, and never commit the machine-specific `.env.local` file. Restart Expo after changing an `EXPO_PUBLIC_` variable.

## API

### `GET /health`

Returns a basic process health response. It does not currently verify database or model availability.

### `POST /classify`

Accepts one multipart form field named `file`. Supported media types are JPEG, PNG, and WebP.

Successful responses contain:

- Scan ID and creation time
- Model identifier
- Top prediction and confidence
- Up to four alternative predictions
- `disposal_status: "local_rules_not_checked"`

### `PATCH /scans/{scan_id}/confirmation`

Accepts one of the labels returned for the referenced scan and saves it as anonymous model
feedback. Labels that were not part of that scan's predictions are rejected.

## Quality checks

Run backend checks from `backend/`:

```bash
.venv/bin/ruff check app tests migrations
.venv/bin/python -m pytest -q
```

The API tests replace the classifier and database session with deterministic fakes. They do not download or execute the Hugging Face model and do not require PostgreSQL.

Run the mobile TypeScript check from `mobile/`:

```bash
npx tsc --noEmit
```

## Known limitations

- The zero-shot classifier recognizes only the candidate categories currently defined in `backend/app/services/classifier.py`.
- Confidence is a model score, not a guarantee that the category is correct.
- Model quality has not yet been measured against a representative waste-item image set.
- The first real classification may be slow while the Hugging Face model is loaded or downloaded.
- Inference currently runs synchronously inside the API request.
- Local recycling rules, municipality selection, official rule sources, and rule freshness checks are not implemented yet.
- The application must not claim an item is locally accepted until an applicable rule has been verified.
- A saved scan-history interface is not implemented yet.
- The health endpoint does not check PostgreSQL connectivity or model readiness.
- Browser access from another LAN device may require additional development CORS configuration.

Model recognition quality should be evaluated separately with a small, labeled collection of real waste-item photographs. Recycling guidance should be evaluated against official municipality or waste-provider sources rather than inferred by the image model.
